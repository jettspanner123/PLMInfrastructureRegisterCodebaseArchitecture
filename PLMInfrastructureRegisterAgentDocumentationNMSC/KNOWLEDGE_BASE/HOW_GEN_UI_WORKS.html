InfraGrid · Chat Assistant Internals

The Clarifying Question

InfraGrid's chat assistant can hand the LLM a button it isn't normally given: the power to stop mid-turn and ask the user something first. This is the one real "generative UI" surface in the whole assistant — everywhere else, the model just writes Markdown. This page traces exactly what happens, byte for byte, from the moment a user types an ambiguous request to the moment the conversation picks back up.

Four tools, one that doesn't behave

Every turn, the backend hands Groq a menu of four callable tools. Three of them run instantly and hand their result straight back to the model. The fourth can't — it needs a human.

query_resources

Looks up Azure VM rows by hostname / environment tag.

resolves instantly
query_environment_overview

Returns logical environment metadata — purpose, sponsor, priorities, status.

resolves instantly
get_environment_action_items

Pulls the free-text action-items log for one named environment.

resolves instantly
ask_clarifying_question

Renders a real interactive card and waits for the user to answer it.

pauses the loop

First, what's a "tool call"?

The model doesn't run code — it asks to.

Groq's Responses API lets the backend attach a list of named functions ("tools"), each with a JSON-Schema description of its parameters. Instead of replying in plain text, the model can emit a function_call item naming one tool and filling in its arguments. The backend then runs real logic, feeds the result back as a function_call_output, and the model keeps going. Three of InfraGrid's four tools are ordinary data lookups. The fourth is where it gets interesting: there's no logic to run — only the user can supply what's missing — so the backend has to stop and come back later.

01
Frontend

sendMessage()

User types something genuinely ambiguous — e.g. "I need you to restart one of the environments" — out of 16 possible environments — and hits send.

  "clientId": "string"

02
Backend

RunGroqConversationLoopAsynchronous

Loads up to 20 prior messages for context, assembles the full conversation array, and calls Groq with all four tool definitions attached. There is no streaming anywhere in this pipeline — it's one plain HTTP request, one plain HTTP response.

POST https://api.groq.com/openai/v1/responses
code · GroqRequestDTO 
{
  "model": "openai/gpt-oss-20b",
  "instructions": "<system prompt: tone, formatting, when to ask>",
  "input": [ /* prior user / assistant turns */ ],
  "tools": [ /* all 4 tool definitions, every call */ ]
}
03
Groq

ask_clarifying_question

The model decides the request can't be answered safely as-is, and instead of guessing — or asking inline in its own prose — it calls the fourth tool, filling in a short heading, a plain- language description, and (optionally) a handful of concrete options for the user to pick from.

code · the tool's own JSON Schema 
{
  "type": "function",
  "name": "ask_clarifying_question",
  "description": "Ask the user a single clarifying question when their request is genuinely ambiguous.",
  "parameters": {
    "type": "object",
    "properties": {
      "heading":       { "type": "string",  "description": "Short title for the question card" },
      "description":   { "type": "string",  "description": "Plain-language explanation of what's unclear" },
      "options":       { "type": "array", "items": { "type": "string" },
                          "description": "Optional — ~5-6 concrete choices" },
      "allowMultiple": { "type": "boolean", "description": "May the user select more than one option?" }
    },
    "required": ["heading", "description"]
  }
}
Backend · the catch

the one tool never in the dispatch switch

Every other tool call gets handed to ExecuteToolCallAsynchronous, a plain switch on tool name. ask_clarifying_question is deliberately left out of it. The loop checks the tool's name before that switch — and if it matches, returns immediately. There's nothing to execute; only the user can supply the missing piece.

code · the loop's own result shape 
GroqConversationLoopResultDTO {
  // exactly ONE of these two branches is ever populated
  Answer?:                   string,
  PendingToolCallId?:        string,
  PendingToolCallArguments?: string,   // raw JSON from Groq
  InputItemsBeforePendingCall?: object[]
}
04
Backend

PersistPendingQuestionAndBuildDTO

Before replying, the backend writes one row that remembers everything needed to pick this exact moment back up — including a full snapshot of the conversation sent to Groq so far.

code · the frozen ChatMessageNexus row 
ChatMessageNexus {
  Role:  "assistant",
  MessageKind: "ClarifyingQuestion",
  ToolCallId:         "call_xyz",
  ToolCallArguments:  "{ heading, description, options, allowMultiple }",
  ToolCallOutput:     null,           // null == still pending
  PendingInputStateJson: "[ ...entire Groq input[] array... ]"
}

Why snapshot the whole conversation? Groq's Responses API has no previous_response_id / server-side memory — every single call must resend the entire conversation from scratch. "Resuming later" doesn't mean telling Groq to continue; it means the backend rebuilding the exact array it had right before the pause, then replaying it.

200 { pendingQuestion, answer: null }
05
Frontend

ClarifyingQuestionCardSharedComponent

pendingQuestion being non-null is the signal — the frontend mirrors it into local state (kind: 'question') and renders the card in place of a normal reply bubble. Clicking an option only stages it; nothing is sent until the user hits Send or Skip.

code · card props 
ClarifyingQuestionCardSharedComponentProps {
  question: { messageId, heading, description, options?, allowMultiple },
  answeredState?: { selectedOptions, freeTextAnswer, isSkipped },  // set once frozen
  onAnswer: (answer) => void,   // the ONE submit path — Send and Skip both call this
  isSubmitting: boolean
}
06
Frontend → Backend

handleAnswerQuestion

The card freezes optimistically the instant Send/Skip is pressed, then fires the answer back — as its own dedicated call, never as a regular chat message.

POST /Api/V1/ChatAssistant/AnswerQuestion
code · AnswerQuestionRequestDTO 
{
  "conversationId": "guid",
  "messageId":       "guid",      // which frozen row this resolves
  "selectedOptions": ["Training"] ,
  "freeTextAnswer":  null,
  "isSkipped":       false
}
07
Backend

AnswerQuestionAsynchronous

Loads the frozen row by messageId, writes the user's answer into ToolCallOutput, then rehydrates PendingInputStateJson back into a real array — reconstructing the exact moment Groq was interrupted — and appends the tool's call plus its freshly-arrived output.

POST https://api.groq.com/openai/v1/responses (resumed)
code · the answer, folded back into the array 
GroqFunctionCallOutputItemDTO {
  type:    "function_call_output",
  call_id: "call_xyz",            // same id Groq originally issued
  output:  "{ selectedOptions: [\"Training\"], freeTextAnswer: null, skipped: false }"
}
08
Groq

the loop continues

With the answer folded in, the model can now call a real data tool (query_resources, query_environment_overview, get_environment_action_items) to actually act on it, answer directly — or, in rarer cases, call ask_clarifying_question again (a nested pause, same mechanism, right from stop 03). A hard cap of 5 round trips per turn keeps this from looping forever.

09
Frontend

back to a normal reply

A final answer is persisted as an ordinary row (MessageKind: "Text") and comes back as { answer, pendingQuestion: null } — rendered client-side as Markdown, same as every other reply in the assistant. The conversation carries on as if nothing paused at all.

GET /Api/V1/ChatAssistant/Conversations useConversationsQuery List a client's conversations for the sidebar.
