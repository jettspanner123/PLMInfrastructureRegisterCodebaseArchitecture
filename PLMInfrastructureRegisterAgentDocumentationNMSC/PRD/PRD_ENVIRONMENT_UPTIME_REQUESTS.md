# PRD: Environment Uptime Requests

## Objective
We need to add a brand-new page called "Uptime Request" to the app. This page lets a user request a planned uptime/downtime window for a specific environment (a date+time range, plus an optional note), and see every such request that's ever been submitted, each tracked under its own sequential ticket number (e.g. `UPTM-00001`). This is a new, standalone feature - not an extension of the existing "Current Uptime Schedule" cell on the Environment Overview table, though it draws its environment list from that same data.

## Core Features
1. A new nav item, "Uptime Request", added to the primary top nav (alongside "Infrastructure Register" and "Environment Overview"), routing to `/environment-uptime-requests`.
2. The page header is a 1:1 copy of the exact header pattern already used by "Infrastructure Register" and "Environment Overview" (the bordered flex-row with a title+subtitle block on the left) - **not** the newer Feature Requests page's header, which uses a different, simpler pattern.
3. A 50:50 side-by-side layout (same convention as the Feature Requests page):
   - **Left 50%**: the submission form.
   - **Right 50%**: the live list of every submitted request.
4. **The form** has exactly three inputs:
   - **Environment** - a searchable dropdown (same `CustomSelectSharedComponent` convention used everywhere else in this app). Populated from the distinct `Environment` values already stored on `EnvironmentOverviewNexus` - but those values are sometimes a single row holding multiple newline-separated names (e.g. `"24x OOTB\n25x OOTB"`); this dropdown splits those into individual options, so each option is always exactly one real environment name.
   - **From** and **To** - one combined date+time picker each (native `datetime-local`-style input), not four separate date/time fields. Both are interpreted and stored in a fixed **CET** timezone, matching how the existing Current Uptime Schedule feature already assumes CET rather than the browser's local time. "To" must be strictly after "From"; a window entirely in the past is allowed (e.g. logging a window after the fact).
   - **Message** - optional free-text textarea, no required length.
5. **The list pane** shows every request as a card, each with: its Ticket ID, the environment name, the From → To range, a status badge, when it was submitted, and the message (truncated with a "Read more" toggle past a reasonable length, same convention as the Feature Requests card). Newest first.
6. **Ticket ID display/interaction** (matching how Jira ticket keys behave):
   - The Ticket ID is rendered as a link whose visible text is just the ticket number itself (e.g. `UPTM-00001`), not a full URL.
   - Clicking that link specifically navigates to that one ticket's own detail/permalink page (`/environment-uptime-requests/UPTM-00001`), showing every field of that single request read-only.
   - Clicking anywhere else on the card (not the Ticket ID link) copies the Ticket ID text to the clipboard and shows a toast confirmation.
7. **Status** is shown as a read-only badge on each card - **not** user-editable on this page. For this build, every request is simply created with status `Pending` and stays there; an admin-only page/flow to actually change a ticket's status is explicitly out of scope here (a possible future feature).
8. **Deletion**: any user can delete any request at any time (soft-delete - `IsDeleted`/`DeletedAt`, same convention as Feature Requests and Environment Overview, with the same confirmation-modal pattern), no ownership restriction (this app still has no real auth system). Deleted requests disappear from the list entirely.
9. **No editing**: once submitted, a request's Environment/From/To/Message can never be changed. If the details need to change, the user deletes the request and submits a new one.

## Ticket ID Generation - Concurrency Design
This is the one piece of real system design in this feature, so it's called out on its own.

- Every request row gets two related identifiers: its normal `Id` (`uuid`, primary key, same as every other entity in this app), and a separate sequential **`TicketNumber`** (`int`).
- `TicketNumber` is generated by a native **PostgreSQL identity column** (`GENERATED ALWAYS AS IDENTITY`) - this is the standard, battle-tested way to hand out gapless-enough, strictly-increasing integers under concurrent inserts. It is **not** implemented as a `SELECT MAX(TicketNumber) + 1` (which race-conditions under concurrent requests); Postgres's own identity/sequence mechanism is internally atomic and lock-free by design, so two simultaneous submissions can never receive the same number, with no extra application-level locking needed.
- The actual displayed **`TicketId`** string (e.g. `"UPTM-00001"`) is a **database-computed, stored generated column** (`GENERATED ALWAYS AS ('UPTM-' || lpad("TicketNumber"::text, 5, '0')) STORED`) - Postgres computes and persists it in the same atomic insert as the identity value, so there is no second round-trip, no read-then-format-then-write race window, and the two values can never drift out of sync.
- A `CHECK ("TicketNumber" <= 99999)` constraint enforces the stated cap at the database level. If a 100,000th ticket is ever attempted, the insert fails loudly (a real error surfaced to the user) rather than silently growing to 6 digits - this fleet is nowhere near that volume, so this is a deliberate "fail loud, decide later" choice rather than a real near-term concern.

## Data Model
New table `IG_EnvironmentUptimeRequestTBL`:

| Column | Type | Notes |
|---|---|---|
| `Id` | `uuid` | Primary key |
| `TicketNumber` | `int` | `GENERATED ALWAYS AS IDENTITY`, `CHECK (<= 99999)` |
| `TicketId` | `text` | `GENERATED ALWAYS AS ('UPTM-' \|\| lpad(...)) STORED` |
| `Environment` | `text` | The single environment name chosen |
| `FromAt` | `timestamptz` | CET-interpreted window start |
| `ToAt` | `timestamptz` | CET-interpreted window end |
| `Message` | `text?` | Optional, user-entered |
| `Status` | `text` | `Pending` \| `Approved` \| `Completed` \| `Rejected` \| `Cancelled` - always `Pending` at creation for this build |
| `CreatedAt` | `timestamptz` | |
| `IsDeleted` / `DeletedAt` | `bool` / `timestamptz?` | Soft delete |

## Tech Stack
- Frontend: React, TypeScript, Tailwind CSS (this app's existing MSC architecture - singleton service, `*CON.ts` constants, TanStack Query hooks)
- Backend: .NET (feature-folder architecture, matching every other feature here)
- Database: PostgreSQL (Neon), via EF Core migrations

## Requirements
- Functional requirements, UI/UX conventions, and business rules are all captured in "Core Features" and "Ticket ID Generation" above - restated briefly:
  - Create, read, and soft-delete endpoints only - **no** update endpoint exists for the request's own fields (immutability is enforced server-side, not just hidden in the UI).
  - No status-change endpoint in this build.
  - The environment dropdown's option list is a derived/split view of `EnvironmentOverviewNexus.Environment`, not a new table of its own.
- Authentication/authorization: none - matches every other feature in this app today (no real auth system exists yet).

## Design Direction
- Header: exact 1:1 copy of the Infrastructure Register / Environment Overview header markup and classes.
- Layout: 50:50 grid, left form / right list, same breakpoint behavior as the Feature Requests page (stacks to one column below `lg`).
- Components reused as-is: `CustomSelectSharedComponent` (searchable dropdown), `CardSharedComponent`, `BadgeSharedComponent`, `ConfirmationModalSharedComponent` (delete confirmation), `EmptyStateSharedComponent` (empty list state).
- Icon: a clock/calendar-style Lucide icon for the nav item (e.g. `CalendarClock`), distinct from the icons already used by the other three nav items.

## Expected Outcome
A working "Uptime Request" page reachable from the primary nav, where any user can submit a request against a real environment and a CET date/time window, see it immediately appear in the list with a freshly-assigned sequential `UPTM-#####` ticket ID, click that ID to open its own permalink page, click elsewhere on the card to copy the ID, and delete the request if it's no longer needed - all fully persisted in Postgres, surviving refreshes and new sessions.

## Constraints
- No editing of a submitted request's fields, ever - delete and resubmit is the only path to a correction.
- No status-change UI anywhere in this build; status always starts and stays `Pending`.
- Ticket numbering is capped at `99999` and fails loudly past that point, by explicit design choice.
- Everything must be real Postgres persistence - no local-only/browser-storage state.
